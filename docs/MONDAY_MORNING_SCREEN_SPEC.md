# Monday Morning Screen：产品与规则大纲

> 状态：设计草案，尚未实施。面向 Harbourside Dental 的黑客松原型，同时把规则写成可处理不同周末来电数据的通用方案。本文不把样本中的姓名、电话或来电 ID 写死为产品逻辑。

## 1. 来源、已定事项与待定事项

| 类型 | 内容 | 依据 |
| --- | --- | --- |
| 正式任务 | 周一 08:00，老板只有 90 秒；设计并展示**一个屏幕**，回答“我先做什么？” | `The_Monday_Morning_Screen_Hackathon_Brief.pdf`，第 1–2 页 |
| 正式约束 | Jade 已接听来电；不要求连接真实 API、电话系统或数据库；可点击原型有效 | 同上，第 1、3 页 |
| 正式约束 | 屏幕要能处理手机、缺失数据、无录音，并顾及柜台患者可能瞥见 | 同上，第 2 页 |
| 用户已定 | 第一屏以**已预约清单**为主体，包含姓名、联系电话、预约时间；不确定或需人工复核使用不同颜色；整体为深色调 | 本项目讨论 |
| 设计建议 | 在预约清单旁保留简短的“现在先处理”区，否则已完成预约可能淹没首要行动 | 由 90 秒评审问题推导；尚待确认布局 |
| 待确认 | 总览是否完整显示电话号码，还是部分遮挡、单条展开后显示完整号码 | 用户展示需求与 brief 的旁观隐私要求需要一起决定 |

正式简报提及 `weekend-calls.json`，当前仓库的 `data/weekend_calls.json` 是**另一份合成示例**，不是所提供 `weekend-calls.pdf` 中的 31 条记录。以下规则应由数据字段与业务配置驱动，样本仅用于检查规则。不要把 PDF 中的个人姓名、完整号码或含临床信息的原始摘要复制到公开仓库文档。

## 2. 任务目标与交付边界

### 2.1 老板在 90 秒内应完成的判断

1. 看见 Jade 已建立的预约：**谁、可联系号码、何时、是否需要核实**。
2. 找到最先需要人处理的事项，并看到简短原因及下一步动作。
3. 发现会影响客户或当天运营的异常：资料缺失、预约时间矛盾、未兑现的回电承诺、取消后可能释放的时段。

屏幕的成功标准是让人从概览走到可执行动作，而不是把所有通话摘要排列成日志。已处理的重复来电、普通问答与低价值噪声保留在可展开记录中，但不抢占首屏。

### 2.2 此次原型不要求实现

- 重新开发 Jade、语音识别、真实电话接入或临床问诊。
- 真实拨号、真实写入 Cliniko、短信、在线数据库或 AI 模型调用。
- 根据不完整日程自动填补取消空档，或把建议匹配宣称为已预约。

若以后要接真实系统，应作为单独阶段，在核对权限、完整日程和业务规则后设计；此次文档不把它写成已获批准的功能。

## 3. Jade 的输入边界与隐私规则

| Jade 的行为 | 规则 |
| --- | --- |
| 可以采集 | 姓名、电话号码、来电者想办的事、是否建立预约。 |
| 不采集或存储 | 症状、健康信息、Medicare 号码以及其他临床信息。 |
| 主动透露临床内容时 | 交给执业人员跟进，Jade 继续处理行政流程；不要把临床细节写成可检索字段、总览摘要或 AI 决策依据。 |
| 录音 | 本案例标记为已启用，但其他诊所可能没有；`recording_available = false` 时屏幕仍须完整可用。 |
| 可见范围 | 前台人员可见；柜台患者可能瞥见。总览避免大字号姓名、电话及敏感自由文本。 |

**源数据冲突必须明确处理：**提供的 PDF 和当前仓库示例中的部分 `summary` 含临床描述，而简报又禁止把临床信息作为数据存储。总览不能直接渲染原始 `summary`。产品只显示非临床的操作标签（例如“需执业人员跟进”）和允许的行政事实。若将来接真实源，原始数据如何接收、脱敏、保留或删除，需由诊所确认并另行设计；本原型不新增症状字段或诊断逻辑。

## 4. 概念模型：不要把一次来电等同于一件待办

| 对象 | 含义 | 为什么单独存在 |
| --- | --- | --- |
| `CallEvent` | 一次来电及 Jade 对该次来电的结果 | 31 通电话不等于 31 个客户或 31 件待办 |
| `ContactGroup` | 可有依据地关联到同一联系人的来电集合 | 多次来电要看最新结果，但保留历史尝试次数 |
| `Appointment` | 一个预约或被取消的时段 | 客户重新预约后，旧时段是否空出仍是独立问题 |
| `WorkItem` | 前台或老板需要完成的一项动作 | 一个联系人可能有多个不同事项；一次通话也可能产生多个动作 |
| `DataIssue` | 缺失、无效或互相矛盾的字段及来源 | 不能默默修正数据，也不能把不确定值当确认值 |

推荐把“是否约成”“预约是否已经核实”“是否还有人工工作”作为**三个不同维度**。来源写 `outcome = booked` 只能显示“Jade 记录为已预约”，不能自动升级为“日历与营业规则均已验证”。

一项 `DataIssue` 建议包含 `issue_code`、受影响字段、严重程度、受阻动作、来源事件、检测规则版本和复核状态。记录**为什么被标记**，而不把原始临床叙述复制进问题说明。

## 5. 通用数据契约与缺失显示

字段以现有来源为准，适配层负责映射；不要求上游恰好使用下表的命名。`null`、空字符串、无效值、互相矛盾、未知，不能混为同一种情况。

| 信息 | 建议标准字段 | 缺失或异常时的屏幕行为 |
| --- | --- | --- |
| 来电身份 | `event_id`、`source` | 无稳定 ID 时生成仅供原型使用的内部键，保留来源位置；不得误合并两次来电 |
| 来电时间 | `received_at`、时区 | 显示“时间未提供/时区待核实”；不做“今天”或超时判断 |
| 联系方式 | `caller_name`、`caller_number`、`callback_number` | 分别显示“姓名未提供”“号码缺失”“号码格式待核实”；来电显示号码不等于已确认的回拨号码 |
| 行政需求与结果 | `intent`、`outcome`、允许的 `flags` | 未知类别进入“待分类/人工复核”；不推断为已解决 |
| 预约 | `appointment.date/time`、`type`、`practitioner`、可选 `duration`、状态 | 来源称已预约却缺时间时，仍列在预约区但标“预约资料待核实”；不编造时长或医生 |
| 录音 | `recording_available` 与可选的可播放媒体引用 | `false` 或无媒体引用时不显示可用的播放按钮；业务摘要和动作照常工作 |
| 处理证据 | 关联事件、判断原因、最近更新时间 | 行动卡须能追溯原因；无证据时显示“原因待核实” |

### 5.1 缺失标记词汇

- **未提供**：上游根本没有该值。
- **格式待核实**：有值但不满足格式或可信度规则。
- **信息冲突**：两个来源或同一记录中的字段互相矛盾。
- **尚未验证**：来源给出结果，但未核对日历、营业配置或联系归属。
- **不可用**：本环境确实没有该功能或媒体，例如无录音。
- **不适用**：该记录原本不需要这个字段，例如普通问答没有预约时间；不能计入“缺失预约时间”。

界面必须说明缺的是**哪一项**、会阻止**哪一步动作**。例如号码无效时，不能给出可点击的“立即拨打”；预约时间缺失时，不能把它排进准确时间顺序。
`flagged` 或 `repeat_caller` 未提供时记为“未知”，不能当成“已检查且没有标记/重复”；字符串 `"false"` 也不能按布尔真值处理。来源加载失败与合法的 0 通电话必须显示成不同状态。

## 6. 从来电到首屏的处理顺序

1. **读取并追踪来源**：接收诊所营业配置、时间区间和来电事件；保留允许使用的行政字段、原始日期/号码及来源定位，不在显示层直接修改原值。涉及临床内容的原始自由文本不得为了追踪来源而再次写入视图、日志或导出文件。
2. **校验与隐私过滤**：检查字段存在性、格式、时区、预约日期与营业时间；从默认显示模型中排除临床自由文本。
3. **关联相关事件**：优先用可信的归一化号码或明确关联 ID；同名仅作人工核对线索，不自动判定同一人。
4. **还原当前结果**：按事件时间追踪预约、取消、重约、未约成、回电承诺等。后续成功预约可解决早期“没有空档”，但不自动解决独立投诉或取消空档。
5. **生成待办与异常**：每项需写明原因、建议动作、证据、阻碍动作的缺失字段及状态。
6. **排序与呈现**：先展示必须处理的事项，同时以已预约清单为主区；普通已解决记录下沉到详情。
7. **记录人的处理**：原型可在本次会话内标记“处理中/已处理”，并真的改变列表状态；不得用只有提示气泡而不变状态的按钮冒充闭环。

重复导入的同一来源、同一事件 ID 且内容相同，只计一次；同 ID 内容不同要标冲突，不能静默覆盖。若记录缺 ID，可用来源文件与行号生成**内部定位键**，但不得称它为 Jade 原始 ID。任一阶段失败时保留仍可读的记录与错误信息，不显示“Jade 已处理全部来电”这类无依据结论。

### 6.1 重复来电与状态覆盖规则

- 一个人多次问同一预约，**最后已约成**：结束“未约成”待办，保留“曾多次尝试”的上下文。
- 同一投诉再次来电而仍无回电：合成一件待办，增加尝试次数和最近来电时间，不能显示为两位客户。
- 先取消再另日重约：不再显示“需联系客户重约”，但原取消时段可作为独立的待核实空档。
- 同一号码可能被多人共用，或一人可能换号码；号码匹配只是关联证据，出现姓名/需求冲突时转人工确认。
- 不同需求不因同一联系人而全部合并；例如已有预约仍可另有费用投诉。
- 归一化号码要记录地区规则和号码来源；格式有效不等于号码归属、回拨意愿或可接通已获确认。不能靠相同姓名、号码后四位或含糊摘要合并身份。

## 7. 预约、取消与营业规则

### 7.1 预约行的状态

| 状态 | 显示与触发条件 | 允许的动作 |
| --- | --- | --- |
| 已记录预约 | Jade 给出 `booked`，基本信息齐全且无已发现冲突 | 显示预约信息；不声称已和真实日历核对 |
| 预约待核实 | 日期/时间/号码/医生缺失，或与营业时间、摘要、其他记录冲突 | 展示具体原因，安排人工核实；不能自动改期 |
| 需人工跟进 | 客户明确要求回电、转介、确认，或业务规则要求人工处理 | 展示负责人或待分配、下一步动作 |
| 已取消/已改期 | 有明确后续事件支持 | 保留事件历史；清理已失效的旧预约任务 |

检查营业时间前要知道诊所时区、营业日、特殊营业安排、预约开始与结束时间。只知道开始时间为 17:00、营业至 17:00，而不知道时长时，只能标“边界待核实”。有取消事件也只代表**可能释放时段**；没有完整日历与服务时长，不自动给候补人“确认预约”。

### 7.2 缺失和冲突不应被颜色掩盖

每个异常至少给出一句可读原因，例如“来源写已预约，但缺少预约时间”“预约日期落在配置的休诊日”“口述回拨号码与来电显示号码不一致”。保留原值供授权人员核查，绝不悄悄改年份、星期或号码。

## 8. 人工复核、优先级与动作闭环

优先级采用**可解释的规则顺序**，而非仅给每通电话加分。规则作用于当前 `WorkItem`，不是作用于孤立的历史事件；同级项目可再按是否临近、承诺时限、最近来电时间和重复次数排序。所有自动排序都应展示理由。

| 层级 | 通用触发条件 | 屏幕上的下一步 |
| --- | --- | --- |
| 立即查看 | Jade 标记紧急、必须由执业人员判断的事项，或即将发生的高影响预约冲突 | 置顶并指明应由谁复核；不显示临床细节，也不自动诊断 |
| 尽快处理 | 已承诺但未完成的回电、重复未解决的投诉、临近预约的资料/时间冲突 | 显示回电或核查原因，并可进入详情 |
| 计划处理 | 明确候补、重新预约、转介请求，以及有联系依据的流失机会 | 列入待办，不能把销售机会冒充紧急事件 |
| 已完成/可收起 | 已约成且无待核实项、普通问题已解答、错误号码等 | 留在可搜索的记录，不抢占 90 秒主视图 |

人工处理状态建议为 `待处理 → 处理中 → 已完成`，另有 `资料不足/无法联系`。状态变化应记录操作者、时间和处理结果；如果只是原型，明确标注这是模拟状态。缺少可用联系方式时，“回电”按钮禁用并解释原因；保留其他可执行动作，例如核对号码来源。

### 8.1 不同来电结果如何产生动作

以下是**建议规则**，不是声称 Jade 已自动执行。处理顺序为“来源明确的标记/承诺 → 数据核验 → 产生人类动作”；`sentiment`、凌晨来电或重复次数只能作为排序线索，不能单独推断医学紧急程度。

| 来电状态或证据 | 建议产生的当前事项 | 避免的误判 |
| --- | --- | --- |
| `urgent_flagged` 或来源 `flagged=urgent` | 置顶，交合适工作人员/执业人员复核 | 不展示症状、不自动诊断；仅靠夜间时间不标医学紧急 |
| 来源写 `booked` | 建立预约行；若资料缺失或营业配置冲突，再建核实事项 | 已预约不等于无其他人工事项，也不等于已核对真实日历 |
| `cancelled` | 记录取消事件及潜在释放时段；若明确要求重新预约，另建回电待办 | 不把全部取消都列为必须回拨；不把时段称为确定可用 |
| `no_availability` | 若反复尝试、请求候补或明确希望回电，建立可跟进事项 | 后续已约成时，关闭同一预约请求的旧待办 |
| `message_taken` 且有投诉、明确承诺或服务范围外转介 | 形成对应部门的待办，合并同一事项的重复催办 | 不仅因负面情绪就当紧急；不擅自推荐没有依据的服务 |
| `failed_callback_number` 或联系方式冲突 | 标“先核对联系方式”，保留联系线索的来源 | 不补猜缺失数字，也不直接把来电显示号码当已确认回拨号 |
| `question_answered`、`wrong_number`、短暂挂断 | 默认收起；若另有独立承诺或有效标记，则保留该待办 | 不把每通未预约都抬成老板首要任务 |
| 来源状态未知、字段互相矛盾 | 进入待分类/资料核实，不按低优先级静默关闭 | 未知不能等同于无需处理 |

同一条已预约记录还可能携带“给执业人员的非临床跟进标记”；预约状态与人工动作分别保留。对尚无完整日程的“空位与候补”只可显示**潜在匹配建议**，不可自动承诺客户。

## 9. 一屏信息架构与深色 UI

```text
┌──────────────────────────────────────────────────────────────────┐
│ Harbourside Dental · 周一 08:00 · 来电/预约/待办/异常摘要          │
├──────────────────────────────────────────────────────────────────┤
│ 现在先做：最高优先级的一件事 + 简短原因 + 下一步动作              │
├────────────────────────────────────────────┬─────────────────────┤
│ 已预约清单（主区）                           │ 其他待处理事项      │
│ 时间 · 姓名 · 电话 · 类型/医生 · 状态          │ 只列未解决事项      │
│ 正常 / 待核实 / 需人工复核，均有文字标签      │ 原因 + 操作        │
├────────────────────────────────────────────┴─────────────────────┤
│ 可展开：取消空档、数据质量、已解决与全部来电                      │
└──────────────────────────────────────────────────────────────────┘
```

- **主体**：用户指定的已预约清单，列出姓名、电话和预约时间。清单数字由输入数据计算，不把“12”写死。
- **行动提示**：始终保留一个可以回答“先做什么”的可见位置。没有待办时明确显示“目前没有需立即处理的事项”；资料加载失败不能显示此句。
- **不同颜色**：建议正常用低强调中性色/青绿，待核实用琥珀色，需人工用紫色，立即查看用红色；最终色值待视觉设计确定。颜色必须辅以标签、图标或左边框，不能单靠颜色。
- **暗色层级**：主表优先保证文字对比度与行间距，异常突出但避免整屏报警色；号码不作为大字号指标。
- **隐私待确认**：姓名和电话作为用户指定字段保留。建议总览只展示足以辨认的紧凑信息，完整号码在授权人员操作单条记录时显示；若坚持总览完整显示，需在设计评审中说明如何降低柜台旁观暴露。
- **手机端**：最高优先行动先于可滚动预约列表；列表行折叠为“时间 + 姓名 + 状态”，号码在该行详情可见，保留同样的操作路径。待办超过首屏容量时显示“还有 N 项”及完整入口，不截断紧急项。
- **详情**：仅显示允许的行政事实、关联事件、异常理由及操作；不把未经清理的原始 `summary` 或录音内容直接贴在默认视图。
- **无录音**：`recording_available = false` 或缺少媒体引用时，不显示失效播放控件；其余信息和动作不依赖录音。

## 10. 交互范围

原型至少应让评委看见：筛选或定位待核实预约、打开具体原因、找到可联系号码、把一项待办标为处理中/已处理并看到计数变化。可以用本地状态模拟，不声称已拨出电话或已写入真实预约系统。任何“预约成功”“已联系客户”字样，都必须有对应的来源事实或用户操作证据。误点“已处理”后应有可撤销或重新打开的路径；若状态仅在本次会话有效，界面要如实说明。

## 11. 以样本核验规则，但不为样本硬编码

以下只作为回归案例。来源为 `weekend-calls.pdf`，3 页；正式简报还称会提供 JSON，当前未取得与该 PDF 完全对应的原始 JSON。

| 样本现象 | 通用规则应给出的结果 |
| --- | --- |
| 三次联系，前两次无空档，第三次已约成（c011/c013/c017） | 聚合为一个联系历史，旧的“未约成”不再是待办 |
| 取消后另日重约（c002/c023） | 不重复催促客户重约；原取消时段独立核查 |
| 同一费用投诉再次来电（c005/c031） | 一件仍未解决的升级待办，显示重复次数与最近来电 |
| 两次无空档，后要求候补（c024/c026） | 一个候补/回电待办；不自动确认与空档匹配 |
| 口述回拨号码少一位，但来电显示字段完整（c009） | 标“联系方式待核实”；不称完全失联，也不自动认定来电显示号码已验证 |
| Jade 标记紧急（c019） | 提醒执业人员优先复核；不存储或展示临床细节 |
| 三条来源称已预约的记录落在配置的休诊日（c006/c010/c027） | 仍在预约区，但显示明确的时间冲突与人工核实动作 |
| 一条预约从 17:00 开始，营业也在 17:00 结束（c030） | 缺少时长时只标“边界待核实”，不直接判为有效或无效 |

样本计数为 31 通来电，其中 `booked` 12、`cancelled` 3、`no_availability` 5。26 个不同来电号码不等于 26 位患者；12 条 `booked` 也不等于 12 条已核实有效的预约。简报举例称“两人取消”，但数据有 3 条取消记录。样本的 2026-11-14 至 2026-11-17 实际是周六至周二，与“周五至周一”场景冲突；部分文字星期也与 ISO 日期不符。这些是来源数据问题，不能自行把年份或日期改成看似合理的值。

## 13. 验收清单

| 场景 | 预期结果 |
| --- | --- |
| 完整、无冲突的已预约记录 | 出现在预约主体，姓名/电话/时间字段可用，来源状态表述准确 |
| 已预约但缺时间、号码或医生 | 保留记录，标出具体缺项；不可显示假时间或可用的错误操作 |
| 预约日期与营业配置冲突 | 异色标记、显示原因、待人工核实；不自动更改原始日期 |
| 同一联系人多次致电，最后已解决 | 历史聚合，失效待办消失；独立的取消空档或投诉仍保留 |
| 多次未解决同一诉求 | 聚合为一个待办，保留次数和最近来电；不重复计为多个客户 |
| 无姓名、无电话或号码冲突 | 明确缺失/待核实，操作按钮与可联系性一致 |
| 未知 `flagged`、错误类型的布尔值、同 ID 不同内容 | 不默认为安全或已解决；给出可定位的数据问题 |
| `recording_available = false` 或无媒体引用 | 无失效播放按钮；仍可看摘要和执行动作 |
| 输入含临床自由文本 | 默认屏不显示临床细节，不创建症状字段或自动诊断 |
| 手机窄屏、空数据、未知 `outcome` | 有清晰布局与安全的空/未知状态，不崩溃也不假报“全部已解决” |
| 点击“已处理” | 待办、计数和状态同步变化，并明确只是原型操作 |
| 0、1、31 或超过 31 通来电；超过 6 项待办 | 数字动态计算，空队列与加载失败区分，余下待办均有可达入口 |

## 14. 三人分工与整合契约（建议）

| 角色 | 独立负责 | 交付给其他两人的契约 |
| --- | --- | --- |
| A：数据与规则 | 数据适配、缺失与异常、关联事件、当前状态及优先级 | 稳定的预约行、待办、数据问题三类视图数据；每项附来源与理由 |
| B：单屏 UI | 深色预约主表、异色状态、手机布局、隐私与无录音状态 | 只消费视图数据，不在界面里重新计算业务优先级 |
| C：交互与展示 | 详情、筛选、原型状态变化、演示路径与提交材料 | 不改变 A 的规则；记录操作后更新同一视图数据；安排三人均能发言 |

合并检查点：同一条有缺失/冲突的预约，在 A 的结果、B 的颜色/标签、C 的详情与动作中必须一致。对外演示只说“原型模拟”或“Jade 记录”，不把无真实集成的结果说成已写入 Cliniko。
